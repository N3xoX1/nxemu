# Performance audit of the validated rendering commit

Baseline: `61f2d4b645b2110c51eee21e981ded8c0f5ca4fc` on `fix/rendering-perf`.
These fixtures measure scaling and preserve the validated renderer. They do not
implement any of the candidate optimizations and do not measure game FPS.

Run the existing CPU extraction and regression suite first:

```powershell
& .\tests\pr396\run-tests.ps1
& .\tests\pr396\run-vulkan.ps1
& .\tests\performance-review\run-cpu.ps1
& .\tests\performance-review\run-readback.ps1
& .\tests\performance-review\run-descriptors.ps1
```

The descriptor fixture additionally requires the production-emitted shader
`build/immortals-menu-diagnostic-20261009/capture-analysis/emit-fixed/4.spv`,
generated by `tests/immortals-gpu/run-shaders.ps1` with the built recompiler.
Paths currently target the installed MSVC v145, Vulkan SDK 1.4.357.0 and bundled
Python runtime, as do the existing fixtures. Results go into
`build/performance-review-20261011`.

`cpu.cpp` reuses the extracted production buffer-cache and version-update bodies.
It exercises unrelated sparse buffers, copy-back through increasing numbers of
resident parts, and a model of the CPU write-mask scan. CPU timings are medians
of seven optimized runs. Sparse copy-back timings exclude mock byte copies and
GPU command execution; counters still verify the exact number and size of copies.
The write-mask scan is a small model, not an extracted full renderer method.

`readback.cpp` submits actual Vulkan atomic writes to a 1028-byte mask, with
transfer-to-compute and compute-to-host barriers. Boundary handles and the
invalid handle are checked word by word with synchronization validation enabled.
Timings then run without validation, alternating two modes over 21 samples
after four warmups. Each immediate dispatch uses submit and queue-wait-idle,
modeling the synchronization boundary rather than instantiating Scheduler.
The batched control has no intervening CPU alias consumers; deferring the
renderer's readback to that point would require additional correctness work.

`generate-descriptors.py` extends the existing GPU storage-array fixture to
arrays of 5, 1025 and 8193 entries per numeric type. It times regular descriptor
writes and update templates, with the template stride matching the renderer's
descriptor payload. The production-emitted shader still uses the first five
handles. This checks that enlarged layouts preserve those image writes and
measures driver update cost, not full shader throughput, descriptor allocation,
or the texture-cache table scan. Large layouts are validated separately;
benchmark numbers come from runs without validation. Generated source hashes
are recorded for reproducibility.

All CPU fixtures use deterministic memory/runtime doubles where described.
Large sparse populations are stress cases; the measurements do not prove those
populations occur in a particular game. The review report records findings,
timings, scope and limitations beside the logs.

Observed on the RTX 5070 Ti with the validated commit and no active game:

| Isolated operation | Median |
|---|---:|
| GPU mask dispatch, submit/wait after each | 64.336 us per dispatch |
| GPU mask dispatches batched without intermediate host consumers | 5.715 us per dispatch |
| Sparse copy-back bookkeeping, 256 resident parts | 52.083 us |
| Template update, three arrays of 8193 typed descriptors | 14.286 us |

The cache's version publisher scans all sparse parts after every written part,
giving quadratic bookkeeping for this copy-back stress case. Runtime image
stores also need a GPU readback before marking precisely the modified images;
the batched control is not a safe replacement for that protocol. These results
identify optimization candidates, not implemented fixes or demonstrated causes
of a particular game's frame rate. Existing synchronization barriers and alias
tracking must be preserved when addressing these costs.
