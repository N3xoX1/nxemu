# Performance audit of the validated rendering commit

Baseline: `61f2d4b645b2110c51eee21e981ded8c0f5ca4fc` on `fix/rendering-perf`.
These fixtures measure scaling and do not measure game FPS. The validated
baseline is retained in Git; the current working tree additionally tests the
conservative sparse reference optimization described below.

Run the existing CPU extraction and regression suite first:

```powershell
& .\tests\pr396\run-tests.ps1
& .\tests\pr396\run-vulkan.ps1
& .\tests\performance-review\run-cpu.ps1
& .\tests\performance-review\run-readback.ps1
& .\tests\performance-review\run-descriptors.ps1
```

The descriptor fixture additionally requires the production-emitted shader
`build/immortals-menu-diagnostic-20261009/capture-analysis/emit-fixed/4.spv`,
generated by `tests/immortals-gpu/run-shaders.ps1` with the built recompiler.
Paths currently target the installed MSVC v145, Vulkan SDK 1.4.357.0 and bundled
Python runtime, as do the existing fixtures. Results go into
`build/performance-review-20261011`.

`cpu.cpp` reuses the extracted production buffer-cache and version-update bodies.
It exercises unrelated sparse buffers, copy-back through increasing numbers of
resident parts, and a model of the CPU write-mask scan. CPU timings are medians
of seven optimized runs. Sparse copy-back timings exclude mock byte copies and
GPU command execution; counters still verify the exact number and size of copies.
The write-mask scan is a small model, not an extracted full renderer method.

`readback.cpp` submits actual Vulkan atomic writes to a 1028-byte mask, with
transfer-to-compute and compute-to-host barriers. Boundary handles and the
invalid handle are checked word by word with synchronization validation enabled.
Timings then run without validation, alternating two modes over 21 samples
after four warmups. Each immediate dispatch uses submit and queue-wait-idle,
modeling the synchronization boundary rather than instantiating Scheduler.
The batched control has no intervening CPU alias consumers; deferring the
renderer's readback to that point would require additional correctness work.

`generate-descriptors.py` extends the existing GPU storage-array fixture to
arrays of 5, 1025 and 8193 entries per numeric type. It times regular descriptor
writes and update templates, with the template stride matching the renderer's
descriptor payload. The production-emitted shader still uses the first five
handles. This checks that enlarged layouts preserve those image writes and
measures driver update cost, not full shader throughput, descriptor allocation,
or the texture-cache table scan. Large layouts are validated separately;
benchmark numbers come from runs without validation. Generated source hashes
are recorded for reproducibility.

All CPU fixtures use deterministic memory/runtime doubles where described.
Large sparse populations are stress cases; the measurements do not prove those
populations occur in a particular game. The review report records findings,
timings, scope and limitations beside the logs.

Observed on the RTX 5070 Ti with the validated commit and no active game:

| Isolated operation | Median |
|---|---:|
| GPU mask dispatch, submit/wait after each | 64.336 us per dispatch |
| GPU mask dispatches batched without intermediate host consumers | 5.715 us per dispatch |
| Sparse copy-back bookkeeping, 256 resident parts | 52.083 us |
| Template update, three arrays of 8193 typed descriptors | 14.286 us |

The cache's version publisher scans all sparse parts after every written part,
giving quadratic bookkeeping for this copy-back stress case. Runtime image
stores also need a GPU readback before marking precisely the modified images;
the batched control is not a safe replacement for that protocol. These results
identify optimization candidates, rather than demonstrated causes
of a particular game's frame rate. Existing synchronization barriers and alias
tracking must be preserved when addressing these costs.

The current candidate skips the global version scan only for canonical buffers
that have never been registered as a sparse part. Registration is conservative
for the buffer's lifetime and is repeated when a part is resolved after buffer
merges or mapping changes. Version numbers still advance on every write, and
referenced buffers retain the existing overlap and disjoint-part behavior.
The fixture also checks construction and move of the actual production
BufferBase, part registration/re-registration, repeated writes and part removal.
An independent oracle compares all sparse versions after 2000 randomized writes
to referenced and unreferenced buffers against the original update semantics.
This eliminates scaling with unrelated sparse populations, while copy-back to
referenced buffers retains its existing cost. Game FPS still requires measurement.

`run-ranges.ps1` compares the current implementation with validated commit
61f2d4b6, extracting both production continuity checks and flush query functions.
It checks monotonic usage coverage against independent 64-byte block bits,
CPU/CachedCPU/GPU upload ranges and protection notifications against the original
WordManager, and mapping changes, holes, fragmentation and contained range reuse.
Continuity cache results are per thread and manager, positive only, and never
retained during a mapping mutation. Mapping scopes invalidate at entry and exit.
Flush presence filtering is tested with both accuracy levels and dirty/clean,
registered/unregistered regions. Scaling benchmarks use large synthetic buffers;
game FPS and visual correctness still require a live run of this candidate.

`run-downloads.ps1` extracts the complete production async download planner and
retirement bodies, comparing to 61f2d4b6. It uses the real MemoryTrackerBase and
RangeSet, with bounds-checked GPU copies into staging storage and guest RAM doubles.
The tracker reports whole pages; the candidate clips each to the committed byte
interval and current buffer before intersecting the GPU dirty byte set. The old
planner duplicates disjoint same-page writes and can include adjacent buffers.
64 four-byte writes produce 4096 copies in the old planner and 64 in the candidate.
300 random sequences compare planned byte multiplicity and retired guest bytes
with independent byte arrays, including CPU cancellations and newer GPU writes.
Full buffer, empty batch, staging offset, untracked page and buffer boundaries
are checked separately. Benchmarks exclude fixture construction, include actual
CPU staging copies, and use seven medians; these are not live GPU transfer timings.

The GPU write history candidate was removed after the v4 game test showed no FPS gain.

`run-coalesced-copy.ps1` extracts the complete production device page walker and
both write methods. It compares the new GPU readback method with the original
on 2000 small sequences and eight 96 MiB cases including physical fragmentation,
holes, aliases, partial end pages and unaligned source pointers. The new method
coalesces only readbacks of at least 96 MiB, and only when both host pointers are
contiguous. It flushes on holes and before returning; all small requests call
the original method. Guard pages check precise end bounds. The benchmark compares
4 KiB memcpy calls and coalescing, including actual copies, across seven medians.
Small warm buffers can regress when copied as one block; they retain the old path.
Large-transfer timings are synthetic and do not prove the size mix of the game.
The opt-in game log records small/large bytes and segment/run counts to verify that.

The download planner also merges adjacent copies only when source buffer ID,
source offset and staging offset are contiguous. The real page tracker test
shows a 128 MiB dirty interval being split into 33 callbacks at 4 MiB manager
boundaries. The candidate emits one copy with the same byte payload. Cancellation
across a manager boundary produces identical guest RAM after retirement. Adjacent
canonical buffers, dirty gaps and staging padding are kept separate. This allows
large contiguous readbacks to reach the physical-span coalescing method rather
than being classified as small due to the tracker's metadata partitions.

GPU readback retirement additionally compares the actual destination before
writing spans of at least 1 MiB. Exact 64 KiB chunks use runtime-selected AVX2
(including OS YMM support) or baseline SSE2 on x64, NEON on AArch64, and memcmp
elsewhere. There are no hashes or retained guest snapshots. Dense changes switch
back to bulk memcpy; CPU cancellation and metadata retirement retain their order.
`run-differential-copy.ps1` tests the helper, and `run-coalesced-copy.ps1` extracts
and tests the complete production walker and readback method against full copies.
`differential-portable.cpp` is a POSIX fixture for GCC/Clang, including every
byte lane, alignment, exact tails, guard pages and random final-byte oracles.
It also runs under AArch64 QEMU and x64 QEMU with AVX2 enabled and disabled.
ARM and older x86 measurements under emulation are correctness tests, not device
performance measurements; no macOS or Android runtime was available locally.

`run-vulkan-delta.ps1` executes the production ReadbackDeltaPass::Copy body and
production host shader against real Vulkan buffers. Nine cases check exact NaN
bit patterns, unaligned descriptor offsets, partial last chunks, consecutive
queued epochs, CPU cancellation and the following GPU write. Synchronization
validation is enabled for these cases and disabled for benchmarks. Twelve timing
rows compare the v8 full transfer plus SIMD retirement with the production delta
pass; each final guest byte is checked outside the timed interval. Command
recording, descriptor allocation, source mutations, submit, fence wait, mask reads
host snapshot updates, live RAM comparisons and retirement copies are timed.
Initial resource allocation/seeding is excluded. Dense changes can regress.
The emulator path retains FIFO retirement, invalidates reference proofs on
RAM changes and falls back for unsupported sizes, offsets or exhausted VRAM budget.
A FIFO host snapshot preserves each GPU epoch and is compared against live RAM,
including untracked RAM writes between queued epochs and canonical buffer removal.
Eligibility rejection counters count checks, which may repeat, rather than traffic.

The user validated the v9 candidate in Immortals Fenyx Rising with correct images
and 35-36 FPS. In matching stable windows (seconds 135-155), logs measured 25.862
system FPS for v8 and 35.247 for v9, a 36.3% improvement across separate runs.
Logical readbacks were 502.9 and 505.6 MB/frame respectively. The candidate avoided
96.16% of readback payload; estimated transferred data fell to 19.42 MB/frame.
Inclusive CPU readback-copy time fell from 20.18 to 10.16 ms/frame. These are game
measurements on Ryzen 9800X3D/RTX 5070 Ti; other games and hardware are unmeasured.
GPU differential readback is enabled by default;
NXEMU_GPU_DIFFERENTIAL_READBACK=0 retains the CPU SIMD path. Reference buffers consume bounded additional VRAM and host RAM.

`run-host-reference-strategies.ps1` compares ten exact host retirement strategies
over four working sets and three change patterns. It rotates order, includes
persistent worker wake/completion and checks every final byte outside timing.
Wider SIMD and finer stores provide little improvement; parallel comparison can
help cache-resident working sets, while large streaming sets remain bandwidth
limited. Synthetic speedups are not predictions of game FPS.

`run-parallel-readback.ps1` checks the production worker class and configured
0/2/4-thread paths. Parts are disjoint, 64 KiB aligned and complete before return;
small spans and overlap retain serial copies. Exact byte oracles, guard pages,
tails and CPU-consumer visibility are checked. The same portable fixture runs
on AArch64 and x86 QEMU, with AVX2 enabled and disabled. Worker creation is lazy,
failure keeps the serial path, and caller-owned TLS prevents overlapping jobs.
`readback_parallel` counts actually split spans. GPU delta remains independent.
`run-cache-filter.ps1` checks the default-enabled monotonic GPU write-history filter and
executes the production Vulkan flush/CPU-write predicates. Its writer variants
compare unconditional atomic RMW at 4/64 KiB granularity and published-word loads.
All historical positives keep the original mutex; only never-written negatives
bypass it. Publication precedes ordinary, DMA-mirrored and sparse dirty ranges.
Existing resource-presence proofs omit absent buffer/texture CPU callbacks while
preserving GPU-dirty early returns and shader invalidation. Real held-mutex tests
verify that positives still block; independent byte/page oracles and concurrent
writers cover false-negative risks. NXEMU_GPU_WRITE_FILTER=0
keeps the previous path. The fixtures also pass native Linux and ARM64 QEMU.
The retirement function now owns the workers through an explicit stack scope;
only a nonowning pointer is TLS. `run-parallel-dll-shutdown.ps1` reproduces the
old TLS-owner deadlock in a disposable Windows DLL fixture and checks repeated
DLL loading, worker completion, caller joining and unloading in 0/2/4-thread modes.
Callers without a retirement scope retain the serial path. This avoids joining
workers from DLL TLS destruction while the Windows loader lock is held.

`ANDROID-NEON.md` describes six AArch64 comparison variants and physical-device
benchmarking. All variants pass exact byte/guard tests under Cortex-A53 and max
QEMU models. Generated NEON instructions were checked; emulated timings are not
used to select a faster mobile implementation. The NDK wrapper is syntax checked,
but an actual Android NDK build and hardware measurement remain unavailable.

The upload tracker additionally summarizes CPU | Untracked work by word. Tests
compare ranges and protection notifications with v9, including cached writes
with zero CPU dirty bits, 64-word boundaries, larger managers and movement. A
noinline benchmark avoids eliminating the clean upload call in the compiler.

The user validated the v12 candidate with correct Immortals rendering and normal
process exit. Stable separate runs requested in the same scene/camera measured
42.769 FPS for v11 and 46.777 for v12 (9.4% higher); a later v12 window measured
46.212. This is an across-run comparison, not a deterministic replay. Logical
traffic remains about 501-504 MB/frame. CPU readback-copy time was 8.16 ms/frame
in v11 and 5.48 in the first v12 window. The filter bypassed 23.0% of buffer-flush
consultations and 93.0% of texture consultations in CPU-write callbacks. Buffer
CPU-write consultation was still required in every measured callback. All
positive predicates and actual copy/fence visibility retain their original locks.

`run-strategies.ps1` compares five experimental real Vulkan paths: full memcpy,
archived v7 SSE2, current SIMD, two CPU threads, and exact GPU comparison with
selective downloads. The GPU reference and source are device-local; staging is
host-visible coherent with cached memory preferred. Timings include transfers,
submissions, waits, CPU retirement, masks, and refresh of the additional GPU
reference following simulated CPU uploads. Initial allocation/reference seeding
is excluded. Final RAM is checked against an independent oracle, with cancelled
CPU bytes spanning chunk boundaries. A follow-up upload refreshes that range
before a new GPU write and verifies detection by the next mask. Vulkan sync
validation runs separately from timing. These worker/GPU strategies are fixtures
only; integrating a mirror requires the emulator's complete alias, cancellation,
remapping and pending-epoch lifecycle. They do not establish game FPS gains.


`run-retirement-audit.ps1` extracts actual fence retirement and raw query RAM
writes. Seventeen controls in serial/four-thread modes verify completed payloads,
lock ordering, newer CPU writes and unchanged GPU epochs after untracked query
writes. Test-only negative controls demonstrate that early unlocking, GPU flags
alone and buffer-only generation counters can lose guest data. No production
lock, readback policy or experimental environment option is changed.
`run-vulkan-delta.ps1 -CorrectnessOnly` runs validation without the benchmark.
Worker tests cover burst/idle wakeup, parked shutdown and idle CPU use; DLL tests
perform a large and small copy before unloading the existing worker scope.


The optional `NXEMU_CURRENT_GPU_DIRTY_FILTER=1` summary tracks current dirty
buffer pages. Three write sites publish before dirty insertion; retirement
refreshes only after exact live-RAM reconciliation and preserves newer GPU
epochs. Texture aliases retain the historical buffer-lock policy. Unsupported
addresses or allocation failure use the conservative path. It is disabled by
default. Tests cover independent byte oracles, publication, cancellation and
held mutexes. In Immortals it bypassed about 43-44% of buffer consultations,
versus 23% for v12, at about 0.028 ms/frame maintenance. Separate runs measured
46.38 FPS for v14 and 46.21-46.78 FPS for v12: no demonstrated extra FPS gain.
Worker polling, invalidation filtering, adaptive eight-thread pools and batching
of memory protections were not retained after their game measurements.


Production defaults (2026-10-15):

| Variable | Unset default | Explicit override |
| --- | --- | --- |
| `NXEMU_GPU_DIFFERENTIAL_READBACK` | Enabled | `0` disables, `1` enables |
| `NXEMU_GPU_WRITE_FILTER` | Enabled | `0` disables, `1` enables |
| `NXEMU_CURRENT_GPU_DIRTY_FILTER` | Disabled | `1` enables |
| `NXEMU_PARALLEL_READBACK_THREADS` | 4 with >=8 logical CPUs, 2 with >=4, otherwise 0 | `0`, `2`, `4` |

Thread counts include the retirement caller: four means three helpers. Explicit
2/4 retains the existing requirement of at least two additional logical CPUs.
Unknown CPU capacity uses serial retirement. Copies below 2 MiB, overlapping
spans and callers without a retirement scope remain serial; worker creation
failure also retains the serial path. This is a conservative capacity policy,
not a measured optimum for asymmetric mobile CPUs or a physical-core count.

The default GPU paths retain the existing size/alignment and memory-budget
fallbacks. Invalid overrides disable the corresponding optimization. Environment
options are sampled once per process (differential readback per runtime).
Mario, Zelda and Immortals rendering was validated with the first two options
and four threads enabled in the comparison launchers. There is no isolated
in-game 0-vs-4 thread comparison, nor measured ARM-device FPS claim. Historical
percentage gains above describe separate complete build runs, not universal
per-option guarantees. The current-dirty filter remains optional because its
extra consultations avoided did not demonstrate an additional FPS gain.

A follow-up OFF/ON comparison on 2026-10-15 used the same CPU/video/OS/loader
DLLs and the same disposable benchmark frontend for every run. Differential
readback and write-history filtering stayed enabled, with four retirement
threads. Mario Odyssey, Zelda Tears of the Kingdom and Immortals each used a
fixed camera after loading the same save. Thirteen 35-second captures were
recorded; the first cold Mario capture was excluded from the primary comparison.
The remaining two captures per condition use complete game-frame intervals
within seconds 5..34, pooled below:

| Game | OFF FPS | ON FPS | Observed change | OFF 1% low | ON 1% low |
| --- | ---: | ---: | ---: | ---: | ---: |
| Mario Odyssey | 197.90 | 198.70 | +0.41% | 146.05 | 143.31 |
| Zelda Tears of the Kingdom | 82.11 | 83.29 | +1.45% | 63.82 | 68.59 |
| Immortals Fenyx Rising | 48.32 | 47.92 | -0.83% | 39.81 | 35.99 |

No graphical anomaly was observed in these scenes. Config/device metadata
matched within each game, with no invalidations or dropped frame samples.
Some captures had unfinished timing scopes at closure; call-duration totals
are incomplete and are not used for the FPS conclusion. The last second is
excluded from the complete frame intervals. Consecutive captures are correlated;
these small differences do not establish a statistically certain causal gain
or regression, and do not establish performance on ARM/mobile hardware.

A separate synthetic test of the extracted production flush predicate showed
why the filter is not uniformly beneficial: eligible retired-buffer queries
fell from 15.27 to 6.14 ns, whereas dirty-positive queries rose from 15.21 to
16.43 ns, texture-alias queries from 15.22 to 16.79 ns, and never-written queries
from 4.93 to 6.16 ns. These are medians of seven rotating OFF/ON rounds with
one million queries each, using an uncontended recursive mutex and simplified
cache contents; they exclude summary maintenance and do not predict game FPS.
The summary correctness fixture passed all 21 controls, including 40,000
independent byte-oracle queries. Keep the current-dirty filter disabled by
default because the game results are mixed, retaining explicit opt-in for
targeted comparisons. The temporary frontend and controller settings were
restored after measurement.
